## 1. Overview

This report documents the novel model developed after the baseline TSP reproduction work. The final
project direction is a **day-ahead mixed-fleet hub-and-spoke transit optimizer** for shared mobility
operations.

The objective is not to solve a single point-to-point routing instance. Instead, the model must plan
an entire service day in advance by combining:

- demand clustering
- hub selection
- mixed-fleet assignment
- route ordering
- feasibility validation

The route-ordering component is learned, while the higher-level hub and fleet logic has also been
prototyped as a learned joint planner in the current validated version.

Reference motivation:

- [Flexible Network Strategy Mixed Fleet Hub-and-Spoke Transit Optimization.pdf](/home/ygn/Documents/RV%20Univ/Simulation/Flexible%20Network%20Strategy%20Mixed%20Fleet%20Hub-and-Spoke%20Transit%20Optimization.pdf)

## 2. Why This Problem

The original `attention-learn-to-route` repository is a strong benchmark for TSP/VRP-style problems,
but it does not directly represent the structure of a real shared-transit system.

The transit problem considered here has the following characteristics:

- heterogeneous fleet sizes
- transfer hubs
- constrained walking radius
- transfer feasibility constraints
- capacity limits
- day-ahead planning rather than online re-optimization
- utilization and punctuality matter in addition to distance

This makes the target task a **hierarchical transit optimization problem**, not a pure shortest-path
or shortest-tour problem.

---

## 3. Constraints Noted During Design

The model and pipeline were designed under the following explicit constraints.

### 3.1 Planning Constraint

The system computes everything **one day in advance**.

That means:

- no live dispatch
- no real-time rerouting
- no mid-day re-optimization loop
- all demand is assumed known before optimization starts

### 3.2 Fleet Constraint

The fleet is heterogeneous:

- feeder vehicles for local pickup/drop-off
- trunk vehicles for higher-capacity movement between hubs

The planner must respect vehicle capacity and role.

### 3.3 Hub Constraint

Passengers cannot be routed arbitrarily.

The system must:

- aggregate requests into hub-aligned clusters
- keep walking radius acceptable
- preserve transfer feasibility

### 3.4 Feasibility Constraint

Any schedule published by the planner must be executable.

That implies:

- no capacity overflow
- no duplicated requests
- no unassigned requests
- route structures must remain internally consistent

### 3.5 Model Constraint

The existing TSP attention model is not sufficient as the final solution because it only solves local
tour ordering. It does not directly model:

- hub selection
- fleet type assignment
- transfer structure
- day-ahead transit planning

So the baseline model can only be reused as a **lower-level route-ordering component**.

### 3.6 Joint Planner Constraint

Once hub choice and fleet assignment were introduced as learned modules, an additional constraint
appeared:

- learned hub selection must still cover all requests
- learned fleet assignment must preserve capacity feasibility
- the learned planner must remain comparable to the heuristic pipeline on the same synthetic instances

This forced the joint planner to be evaluated as a full day-ahead pipeline, not just as isolated
classification heads.

---

## 4. Baseline Models

Three baselines were used during development.

### 4.1 Nearest-Neighbor Heuristic

This is the simplest route-ordering baseline inside the transit pipeline.

It:

- starts from the hub
- repeatedly selects the nearest remaining stop
- returns to the hub at the end

This baseline is fast and strong for the synthetic transit scenarios used here.

### 4.2 Pretrained TSP Attention Model

The original pretrained TSP attention checkpoint from the repository was also tested as a route
ordering module.

It was useful as a transfer baseline, but it did **not** outperform the heuristic in the transit
setting.

### 4.3 Transit-Specific Learned Route Orderer

This is the key novel learned component.

It was trained on synthetic transit routes generated by the day-ahead mixed-fleet pipeline, with
2-opt-improved labels.

This model became the default route-construction component because it outperformed both the heuristic
and the transferred TSP attention model.

### 4.4 Learned Joint Planner

The next-stage extension is a learned joint planner for:

- hub choice
- fleet assignment
- route ordering

The current implementation uses a learned scorer for candidate hubs and candidate vehicles, while
preserving the day-ahead feasibility rules. It is not yet superior to the route-order-only model on
route length, but it does change utilization and route composition in a measurable way.

## 5. Proposed Architecture

The implemented system is modular.

### 5.1 Demand Clustering

Requests are grouped into spatial clusters.

This identifies:

- dense service regions
- candidate transfer hubs
- route fragments that can be planned together

### 5.2 Hub Proposal

Each cluster produces a hub proposal based on:

- demand
- compactness
- temporal spread
- access cost

### 5.3 Mixed-Fleet Assignment

The planner assigns feeder and trunk vehicles to the hub proposals.

This module:

- respects vehicle capacity
- assigns requests to specific vehicles
- keeps the fleet structure feasible

### 5.4 Route Construction

This is where the learned model is used.

The route-ordering layer chooses the stop order inside each assigned route.

Implemented options:

- heuristic nearest-neighbor
- pretrained TSP attention decoder
- transit-specific learned route-ordering model

The learned model is the default in the current day-ahead pipeline.

---

## 6. Training Strategy for the Novel Model

The learned route-ordering model was not trained on the original TSP benchmark.

Instead, it was trained using:

- synthetic clustered transit instances
- the day-ahead hub-and-spoke pipeline
- route labels refined with a 2-opt local improvement step

This makes the model transit-specific rather than TSP-specific.

The learning objective is route-order prediction, not full network design.

## 7. Validation Setup

The model was validated at three levels.

### 7.1 Route-Ordering Benchmark

Compared:

- heuristic
- pretrained TSP attention
- transit-specific learned orderer

### 7.2 Full Pipeline Benchmark

Compared the same three strategies inside the full day-ahead transit pipeline.

### 7.3 Custom Instance Benchmark

A custom synthetic transit instance generator was used to confirm that the model works beyond a single
fixed seed.

---

## 8. Final Results

### 8.1 Route-Ordering Benchmark

On 20 synthetic benchmark instances:

| Strategy | Mean route length | Wins vs heuristic |
|---|---:|---:|
| Heuristic | 0.867255 | 20 |
| TSP attention | 1.014257 | 0 |
| Learned transit orderer | 0.828558 | 17 |

Interpretation:

- the pretrained TSP attention model does not transfer well to the transit setting
- the learned transit orderer improves on the heuristic on average
- the learned model is the best route-ordering component in the current system

### 8.2 Full Pipeline Benchmark

On the full day-ahead pipeline:

| Strategy | Mean route length | Mean utilization |
|---|---:|---:|
| Heuristic | 0.889041 | 0.701506 |
| TSP attention | 0.973619 | 0.701506 |
| Learned transit orderer | 0.827686 | 0.701506 |

Key point:

- utilization is unchanged because fleet assignment is held constant
- route length improves when the learned orderer is used

### 8.3 Custom Instance Benchmark

On a custom synthetic instance:

| Strategy | Total route length | Utilization |
|---|---:|---:|
| Heuristic | 1.024704 | 0.750000 |
| TSP attention | 1.021507 | 0.750000 |
| Learned transit orderer | 0.913460 | 0.750000 |

This confirms the learned orderer is also effective beyond the original benchmark seed.

### 8.4 Joint Planner Benchmark

The learned hub-selection and fleet-assignment modules were added to the day-ahead planner and
validated with a joint benchmark.

Current short-run benchmark results:

| Strategy | Mean route length | Mean utilization |
|---|---:|---:|
| Heuristic | 0.901793 | 0.697544 |
| Learned route order only | 0.835070 | 0.697544 |
| Joint learned hub + fleet + order | 1.075017 | 0.723439 |

Custom instance result:

| Strategy | Total route length | Utilization |
|---|---:|---:|
| Heuristic | 1.024704 | 0.750000 |
| Learned route order only | 0.913460 | 0.750000 |
| Joint learned hub + fleet + order | 0.925462 | 0.750000 |

Interpretation:

- the joint planner is functional and demand-safe
- it changes utilization and route count in the batch benchmark
- it stays close to the route-order-only model on the custom instance
- it does not yet beat the route-order-only model on route length
- the learned hub and fleet modules are therefore valid, but still need more training and tuning

## 9. Final Outcome

The final outcome of the project is:

1. a validated day-ahead mixed-fleet hub-and-spoke transit pipeline
2. a transit-specific learned route-ordering model
3. a stronger route-ordering baseline than the pretrained TSP attention model
4. a learned hub-selection and fleet-assignment prototype
5. a benchmark-backed claim that the learned orderer is the best current route-construction module

What the model does **not** yet do:

- learned hub selection
- learned fleet assignment
- dynamic re-optimization
- end-to-end transit policy learning

So the current novelty is real and validated, but it is still a **partial transit optimizer** rather than a fully learned operational system.

---

## 10. Conclusion

The original TSP baseline was useful only as a starting point.

The final novel contribution is the transit-specific route-ordering model embedded inside a day-ahead
mixed-fleet hub-and-spoke planning pipeline, with an additional learned joint-planner prototype for
hub choice and fleet assignment.

The strongest validated result is that the learned route-ordering model outperforms both:

- the nearest-neighbor heuristic
- the transferred pretrained TSP attention decoder

This means the model is not just a repackaged TSP solver. It is a transit-aware route-ordering module
that better fits the project’s operational constraints and benchmark scenarios.

The learned joint planner is also valid, but in the current short-run training regime it is not yet
better than the route-order-only model on route length. Its main demonstrated advantage is improved
utilization in the batch benchmark, a closer custom-instance match to the learned-order baseline, and
a correct learned decomposition of hub and fleet decisions.
